# Gazet SQL (Qwen3.5-0.8B, LoRA)

A 0.8B model that writes **DuckDB spatial SQL** from a question and short descriptions of the tables. It is small
enough to run on a laptop CPU, and is meant as a tool for people and for LLM agents that need to query geospatial
tables (parquet files with geometry columns) without a large model.

Status: first training run (`sql-v1-r16`), private, for evaluation. Not ready for use outside the project.

## Files

Each training run has its own folder:

| Path | What |
|---|---|
| `sql-v1-r16/gguf/gazet-sql-v1-r16-q8_0.gguf` | for llama.cpp (834 MB); same accuracy as the GPU model on a 60-question check |
| `sql-v1-r16/gguf/gazet-sql-v1-r16-q4_k_m.gguf` | smaller (542 MB); not evaluated yet |
| `sql-v1-r16/merged/` | full 16-bit weights (transformers) |
| `sql-v1-r16/adapter/` | the LoRA adapter on top of `unsloth/Qwen3.5-0.8B` |
| `sql-v1-r16/predictions/` | the model's answers to the test sets |
| `sql-v1-r16/log_history.json`, `config.json` | training loss and settings |

## Input format

System prompt:

```
You write DuckDB spatial SQL. Answer with a single read-only SELECT statement and nothing else.
```

User message: one schema card per table, an optional block of value hints, then the question.

```
TABLE jp_prefectures  -- The 47 prefectures of Japan with Japanese and English names. Polygons. rows=47
  nam VARCHAR  -- distinct~47 e.g. ['Aichi Ken', 'Akita Ken']
  ...
  geometry GEOMETRY('EPSG:4326')  -- types=['MULTIPOLYGON'] extent=[...]

VALUES matching the question:
  jp_prefectures.nam: 'Yamagata Ken', 'Fukushima Ken'

Question: Area in km2 of Fukushima minus Yamagata
```

The prompt must be built the way training built it: `student.py`, `hints.py` and `harness.py` in
`dataset/generative/` of the gazet repository. Queries assume `LOAD spatial` and `SET geometry_always_xy = true`.

**Turn thinking off.** The model was trained without Qwen3.5's thinking mode. llama-server turns it on by default;
pass `"chat_template_kwargs": {"enable_thinking": false}` in each request (or start the server with it). With
thinking on, the model writes long reasoning and is much slower.

```bash
llama-server -m gazet-sql-v1-r16-q8_0.gguf -c 4096 -t 6 --jinja
```

## Training

- Base: `unsloth/Qwen3.5-0.8B`; LoRA r=16, alpha=32 on attention and MLP; 2 epochs, learning rate 2e-4, batch 64,
  loss on the answer only. One A100 on Hugging Face Jobs, 20 minutes (`finetune/train_hf_jobs_qwen35.py`).
- Data: 19,419 question/SQL pairs over 23 tables (`chatml/v1` in the private dataset
  `developmentseed/gazet-generative-sql`). Questions and SQL were generated by DeepSeek-V4.1-Flash from real rows,
  every query was executed, and an LLM judge (MiniMax-M3) kept the correct ones. A third of the prompts carry value
  hints. Pairs that need information the prompt does not show were removed.

## Evaluation

Execution match: the model's SQL and the reference SQL are both run and the results compared, ignoring row and
column order. "Lenient" accepts extra columns. 95% bootstrap intervals in brackets.

| Test set | runs | exact | lenient | lenient with hints |
|---|---|---|---|---|
| dev: 755 new questions on the training tables | 91.3 | 62.0 | 69.3 [66-73] | 70.3 [67-74] |
| gold: 342 questions on 8 tables never seen in training | 83.3 | 36.3 | 44.2 [39-49] | 48.5 [43-54] |

Reference models on gold (lenient, no hints, with a longer rules prompt): Mistral Large 4.0 83.3,
gpt-oss-120b 56.4, Qwen3 Coder Next 47.1.

Speed with the q8_0 GGUF on an 8-core cloud VM (6 threads): median 6 s per question; prompts of 500-1,000 tokens are
read at about 200 tokens/s and answers written at 25-40 tokens/s.

## Limitations

- **New tables are much harder than known ones** (44% vs 69%). The model has partly memorised its 23 training
  tables; when its SQL fails to run, it is usually because it used a column or table that does not exist.
- The gold set was filtered by agreement with another model and leans towards easier questions; the base model
  without fine-tuning has not been measured on it yet.
- Training questions are synthetic. None come from real users or agent traces.
- Only DuckDB dialect, lon/lat EPSG:4326 geometry columns named `geometry`, and the card format above were seen
  in training.
- Generated SQL should run in a read-only, sandboxed connection with a time limit.
